# Редактор электрических схем для Arduino и ESP32

Курсовой проект: десктопный редактор электрических схем с футуристичным интерфейсом, встроенным редактором кода, конструктором микросхем, симуляцией и 3D-видом.

## Карта проекта

Решение `CircuitEditor.sln` состоит из пяти проектов. Настройки SDK и языка находятся в `global.json` и `Directory.Build.props`.

| Проект | Зависимости и назначение |
|---|---|
| `CircuitEditor.Core` | `net8.0`, без ссылок на другие проекты и WPF. Модель проекта, электрические расчёты, проверки, история, генерация и анализ кода. |
| `CircuitEditor.Infrastructure` | `net8.0` → Core. Реализации репозиториев в `Repositories/`, встроенные JSON в `Library/` и `Data/`, миграции в `Documents/`. |
| `CircuitEditor.Simulation` | `net8.0` → Core. Виртуальные часы `ISimulationClock` и событийный движок `ISimulationEngine`. |
| `CircuitEditor.App` | `net8.0-windows` → Core, Infrastructure, Simulation. WPF и AvalonEdit. Регистрация зависимостей в `Program.cs`, интерфейс в `Views/`, `Controls/`, `Resources/`, ввод в `Interaction/`, команды и состояние UI в `ViewModels/`. |
| `CircuitEditor.Tests` | `net8.0-windows` → все четыре проекта. xUnit, включая проверки WPF. |

- `Core/Models/CircuitProject.cs` объединяет электрическую модель, два размещения, breadboard, привязки и скетч. `Core/Simulation/SimulationState.cs` хранит неизменяемый снимок времени и состояния сеанса.
- `Core/Netlist/` — `INetlistBuilder` / `NetlistBuilder` объединяет группы отверстий, привязки, внутренние связи и перемычки. `App/ViewModels/ProjectViewModel.cs` перестраивает netlist перед уведомлением `ModelCommitted`.
- `Core/Validation/` — `IErcService` / `ErcService` выполняет набор `IErcRule`. `PinDirectionRule` зарегистрировано, но пока возвращает пустой список.
- `Core/Electronics/` — `IDcSolver` / `DcSolver` рассчитывает поддерживаемые статические цепи. `ProjectAnalysisViewModel` связывает ERC и DC с нижней панелью.
- `Core/History/` — `IEditCommand`, `ProjectEditCommand`, `ProjectSnapshot`, `CommandHistory` (200 действий). `ProjectViewModel` управляет жестами и Undo/Redo схемы. У скетча своя история AvalonEdit.
- `Core/Code/` — `ICodeGenerator` / `ArduinoCodeGenerator`, `ICodeAnalyzer` / `ArduinoCodeAnalyzer`. `CodeViewModel` управляет скетчем, `ICodeAnalysisService` запускает фоновый анализ. Генератор обновляет секции `<auto>` по netlist и шаблонам.
- `Core/Repositories/` содержит `IProjectRepository`, `IComponentLibraryRepository`, `IFootprintRepository`, `IBreadboardRepository`, `IElectricalLibraryRepository`, репозитории шаблонов, дополнения, справки и экспорта. `ProjectSessionViewModel` координирует сохранение, открытие и восстановление через репозиторий проекта и `IDialogService`.
- `.circ` — JSON с `schemaVersion: 2` и `libraryVersion: "1"`. `Core/Documents/ProjectDocument.cs` описывает экземпляры по ID, счётчики, размещения, привязки, провода, состояние вида и скетч. `JsonProjectRepository` читает и пишет файл. `ProjectMigrationV1ToV2` добавляет пустой скетч, `ProjectDocumentResolver` проверяет ссылки на библиотеку и восстанавливает модель.

Из корня решения на Windows с .NET SDK 8.0.425 или более свежим патчем ветки 8.0.4xx:

```powershell
dotnet build CircuitEditor.sln
dotnet test CircuitEditor.sln --no-build --no-restore
dotnet run --project CircuitEditor.App
```

Проверка при составлении карты: Debug собран с 0 ошибок и 0 предупреждений. Тесты — 408 пройдено, 0 упало, 0 пропущено.

- После каждого этапа дополнять этот файл списком выполненного; выводить дерево исходных файлов и подтверждать соблюдение архитектурных правил.

## Обязательный стек

- Только C# 12, .NET 8, WPF. XAML — только разметка и стили.
- MVVM: CommunityToolkit.Mvvm. DI: Microsoft.Extensions.DependencyInjection.
- Редактор кода: AvalonEdit (ICSharpCode.AvalonEdit).
- 3D: HelixToolkit.Wpf; актуальную версию проверять в NuGet. Все модели строить процедурно из примитивов, внешние модели запрещены.
- Скрипты микросхем: Microsoft.CodeAnalysis.CSharp.Scripting.
- JSON: System.Text.Json. Тесты: xUnit.

## Архитектура (нарушение = переделать)

- CircuitEditor.Core: модели, валидация, расчёты; без зависимости от UI, WPF, System.Windows и ViewModels. Проверять ссылки в csproj.
- CircuitEditor.Simulation: движок симуляции, зависит от Core.
- CircuitEditor.Infrastructure: реализации репозиториев и доступ к хранилищам; интерфейсы находятся в Core. Проект создан на этапе 3, JSON-библиотека и данные корпусов/breadboard перенесены в него.
- CircuitEditor.App: WPF, ViewModels, Views; связывает реализации через composition root и DI.
- CircuitEditor.Tests: xUnit; тесты моделей, репозиториев, расчётов и ViewModel соответствующего этапа.
- Один класс = один файл. Файл не длиннее примерно 300 строк, иначе разбивать. Не помещать несколько классов в один файл.
- Строгий MVVM. View (XAML) не содержит логики. Code-behind без логики: пустой или только InitializeComponent.
- ViewModel не создаёт View, не использует MessageBox/Dispatcher напрямую. Взаимодействие с UI — через интерфейсы сервисов, например IDialogService.
- Каждый новый сервис имеет интерфейс и регистрируется в DI.
- Весь доступ к хранилищам (JSON проекта, библиотека компонентов, .chip, скетчи) только через репозитории: интерфейсы в CircuitEditor.Core, реализации в CircuitEditor.Infrastructure.
- Сервисы работают с моделями и получают данные через репозитории; не читают и не записывают хранилища напрямую.
- Сервисы без хранилища (тема, диалоги, навигация) остаются просто сервисами; формальные репозитории для них не создавать.
- Раскладка условных символов считается в Core/Layout через ITextMeasurer. Размеры реалистичных корпусов задаются данными и геометрией контактов; не вычисляются по длине подписей.
- Публичные классы Core имеют XML-комментарии. Без магических чисел. Ошибки обрабатываются без падения приложения.
- После каждого этапа: dotnet build, dotnet test, дерево файлов, подтверждение выполнения правил, краткий отчёт и ручная проверка. Сборка без ошибок и предупреждений, тесты проходят.
- Новые правила имеют приоритет над историческими отчётами в архиве. Прежний лимит 450 строк заменён на ~300. Старые упоминания JSON-реализации в Core относятся к этапу 2, на этапе 3 она перенесена в Infrastructure.

## Принятый курс: Tinkercad-подход

- Главный режим — «Макет»: реалистичные векторные/процедурные корпуса, платы с разъёмами и подписанными контактами, breadboard и перемычки.
- Одна модель проекта, общие идентификаторы компонентов и электрические связи; отдельные размещения и трассы для представлений.
- «Схема» — производное представление: символы перемещаются вручную, соединения редактируются в «Макете».
- В первой версии одна breadboard и фиксированный набор корпусов. Отверстия и электрические группы задаются данными, выводы компонентов привязываются к отверстиям.
- Симуляция Arduino/ESP32 ограничена поддерживаемыми сценариями и управлением пинами: ручным либо через простой встроенный сценарий. Произвольный C++ не исполняется.
- Roslyn применяется только для C#-скриптов микросхем, не для исполнения скетчей Arduino/ESP32.
- Визуальная реакция элементов получает данные из общей симуляции: свечение LED, угол серво, текст LCD.
- Этап 3D-просмотра обязателен по требованиям курсовой и предшествует финальной полировке.

## Принятые решения

Этот раздел фиксирует согласованные решения. Исторические отчёты в архиве могут описывать прежний интерфейс.

- Главный режим — «Макет» по принятому Tinkercad-подходу: реалистичные процедурные корпуса и breadboard. Условные символы сохранены во втором представлении «Схема» того же проекта. Соединения редактируются в «Макете», символы «Схемы» перемещаются независимо; отдельные электрические модели для представлений не создаём.
- Одна breadboard и фиксированные корпуса в первой версии. Геометрия контактов и топология отверстий задаются JSON, а не размерами/соединениями в рисовальщике. Гибкий шаг осевых ножек ограничивается minSpan/maxSpan; масштаб и допуск привязки сосредоточены в PhysicalSettings.
- Core не зависит от WPF. Раскладка символов использует ITextMeasurer; реальные корпуса задаются физическими данными. Новые сервисы — через интерфейсы и DI. Файловый доступ — через репозитории Core/Infrastructure; формальные репозитории для темы, диалогов и навигации не создаём.
- Внешние картинки и готовые 3D-модели не используем: все 27 макетных корпусов процедурные, будущий обязательный 3D — тоже из примитивов.
- .circ хранит экземпляры и библиотечные ID с libraryVersion, без встроенных определений штатных компонентов/корпусов/breadboard. Пользовательские .chip относятся к будущему этапу. Текущий schemaVersion — 2; реализована настоящая миграция 1→2 с пустым скетчем. Фиктивную производственную миграцию до появления старых файлов не вводили; будущие неизвестные версии отклоняются.
- Электрическая связность перемычки определяется концами по стабильным ID, а не цветом, изгибом или пересечением линий. Общая история схемы ограничена 200 действиями: один жест — одна команда, Esc отменяет жест без записи. Текст использует независимый Undo/Redo AvalonEdit, чтобы не засорять историю схемы и не теряться при её отмене.
- Генератор работает через Netlist и ограниченные JSON-шаблоны. Обновляет только секции globals/setup/loop внутри <auto>, сохраняет ручной код снаружи и не переписывает его автоматически при изменении схемы. «Подготовить» безопасно добавляет пустые секции в простой ручной setup/loop; неоднозначный или повреждённый текст не исправляется догадками.
- Плата выбирается по семейству и при необходимости по экземпляру. «Авто» допустимо для единственной платы данного семейства; неоднозначные назначения GPIO не угадываются. Серво: Servo.h для Uno/Nano, ESP32Servo.h для ESP32; требование ШИМ-пина принято по прямому уточнению пользователя. GPIO34–39 ESP32 проверяются как input-only по таблице, без роли из симуляции.
- Полный C++-парсер, компиляция и запуск произвольных скетчей не делаются. Для будущей симуляции согласованы только поддерживаемые сценарии и ручное/сценарное управление пинами. Roslyn предназначен только для скриптов микросхем.
- Последний согласованный интерфейс: компоненты слева, рабочие вкладки сверху, только свойства справа, одна нижняя панель «Проблемы / Расчёт DC / Вывод». Списки ошибок схемы, кода и DC объединены, чтобы команды, результаты и проблемы не были разнесены по разным сторонам окна. Размеры, закрепление, скрытие и возврат панелей сохранены.
- Ошибки можно копировать и открывать в локальной справке с поиском; статьи загружаются из JSON через репозиторий. Периодические строки «анализ: найдено N проблем», включая нули, из вывода удалены. Проблемы показываются в списке, одинаковые последовательные ошибки вывода не дублируются; успех операции сообщается кратко в редакторе.
- SVG экспортируем только для «Схемы»; PNG — для обоих представлений. BOM — CSV UTF-8 с BOM и разделителем «;». Экспорт .ino создаёт одноимённые папку и основной файл.
- Проект «ку» и его автосохранение проверялись чтением, без перезаписи схемы пользователя. Не заменять его демонстрационной схемой и не считать подготовку текстовых маркеров исправлением электрических соединений.
- Автоматическое создание коммитов ранее отменено пользователем. Для последней правки были отдельные явные задания на начальный и финальный коммиты, оба выполнены (9d6ca01, ae3a336). Это история выполненных указаний, а не основание автоматически коммитить каждое следующее действие. Push без отдельного задания не выполнять.
